# tpt-statera

> **Status: Phase 1 code and proofs in place (exit review open), Phase 2 in progress.** The §2 guarantees are **target architecture**
> until the host integration and cross-process concurrency control are verified in a live environment. What exists:
> the single-transfer validator `validate_transfer` with its proofs, a Floor-only rounding policy with tiered
> fees and fee splits (not yet wired into the validator), an in-process ledger, and a CosmWasm adapter that has
> not yet run on a live chain. It does not deliver host-level enforcement on a live chain, cross-process
> atomicity guarantees beyond the single-writer service, or a completed compliance mapping.
> See [THREAT_MODEL.md](THREAT_MODEL.md) before citing any claim.

`tpt-statera` is a pure-Rust, domain-agnostic engine for validating financial state transitions and
enforcing economic invariants. It treats each balance update, transfer, or fee calculation as a
conservation-of-value problem, and aims to back that with machine-checked proofs (via `tpt-telos`)
and explicit dust accounting. It is intended as a verification layer for DeFi, payments, tokenomics,
and supply-chain settlement.

## Quick start

Validate a transfer and, if it is refused, say why. This is the output of the runnable example
`crates/tpt-statera-core/examples/quickstart.rs`:

```rust
use tpt_statera_core::prelude::*;

let state = SystemState::new(1_000, 0, 0); // sender, recipient, treasury
match validate_transfer_explained(state, TransferProposal::new(500, 100)) {
    Ok(outcome) => println!("{outcome}"),
    Err(reason) => println!("denied: {reason}"),
}
```

```text
500 @ 1%:   allow: fee 5, dust 0 retained by sender
1000 @ 1%:  denied: sender balance is below the amount plus the fee
```

`validate_transfer` is the proven function and returns a bare `Deny`. `validate_transfer_explained`
returns the first failing check as a `DenyReason`. A test checks that the two never disagree.
Run `cargo run -p tpt-statera-core --example quickstart` to reproduce the output.

Optional features (off by default, so the core crate keeps zero default dependencies):
`tpt-statera-core/serde` and `tpt-statera-policy/serde` derive `Serialize` and `Deserialize`. Configuration
types are checked on load, and unknown fields are refused.

## Try it

```sh
cargo test --workspace
cargo run -p tpt-statera-runtime --example payments
cargo run -p tpt-statera-runtime --example reference_settlement -- out
cargo clippy --workspace --all-targets -- -D warnings
cargo doc --workspace --no-deps
```

Proofs require a `tpt-telos` build (`cargo build --release -p tpt-telos` in the sibling TPT repo):

```sh
telos verify --solver z3 proofs/transfer_validator_full.telos
telos verify proofs/composition_two_transfers.telos
telos verify proofs/netting_10party.telos
telos verify --solver z3 proofs/floor_fee_exact.telos   # nonlinear: needs the z3 build
telos verify --solver z3 proofs/policy_tiers_3.telos    # policy: three-tier selection
telos verify --solver z3 proofs/policy_split.telos      # policy: fee split conservation
python scripts/verify_proofs.py --telos path/to/telos --solver z3   # every proof, and every negative control must fail
python scripts/generate_certificate.py --telos path/to/telos
```

The reference settlement run regenerates the certificate when `TPT_TELOS` points at that `telos` binary.
Without it, the run copies the committed certificate and says so in its manifest.

## Verify without installing anything

Checking the committed certificate needs only Rust. It does not need a solver:

```sh
cargo run -p tpt-statera-cli -- cert verify proofs/certificate.json --root .
```

This confirms the certificate matches its inputs and its caveat. It does not re-run the solver.

To re-run every proof, build the pinned solver environment in Docker. It needs Docker only, with no Z3 or telos
on the host (todo 5D.03):

```sh
docker build -t tpt-statera-proofs .
docker run --rm tpt-statera-proofs
```

The image is built from `Dockerfile`. It is not verified on GitHub. The GitHub Action
`.github/actions/verify-certificate` runs the same checks in CI.
